# Weightless research goals

Weightless aims to let a person specify what a program owes its caller and leave the choice of implementation and execution target open. The **semantic hypercube** organizes the choices a compiler could make about representation, evaluation order, and execution strategy. Which combinations preserve a given contract? Today the project records individual answers as relationships between graphs, with a contract, evidence, and a verdict. [Original project notes](<docs/Project Weightless.docx>) · [First semantic cube records](experiments/semantic-cube-v1.json)

**The next milestone is a frozen vocabulary that encodes a held-out collection of programs in at most one tenth of the baseline bytes, including the cost of the vocabulary, and reproduces the behavior each program promises its caller.** Tenfold compaction across unfamiliar programs is an open research target. The existing experiments give us reasons to try it and examples precise enough to tell us when it fails.

For each program-encoding experiment, the primary outputs are the **caller-behavior verdict** and the **change in complete encoded size against a named encoding of the same behavior**. A tie or an expansion answers the size question. Keep the measured direction, both byte counts and the cost of any shared material visible alongside the replay results. [Contribution and measurement guidance](CONTRIBUTING.md#what-a-reviewer-needs)

## What should earn a place in the vocabulary?

A base-1024 digit can select one of 1,024 meanings in ten packed bits. The research question is how much recurring behavior a meaning can express. A keyword can name a typed operation with parameters for its magnitude, operands, and policy. A run can carry the number of repetitions. A traversal can take its length from the runtime input. With all other costs equal, ten-bit tags break even with eight-bit tags when a program needs 20% fewer tags. Greater savings depend on how much structure each keyword lets the decoder recover.

- **Repeated work.** A checked-Add run reduced a 4,095-Add image from 20,364 bytes to 21. The count and operand references let the decoder reconstruct every Add. The same encoding saved zero additional bytes on a buffer graph containing one Add. Both results belong in the comparison. [Capacity measurements](experiments/0007-Capacity/README.md#v3-experiment)
- **Shared names.** A 154-byte property map spent 140 bytes identifying receivers and members. Can a family of independently written mappings share those names cheaply? The map must still distinguish which getter feeds which setter and what the caller sees if the second write fails. [Mapping evidence](experiments/0011-PropertyMapping/README.md#v1-results)
- **Shared behavior.** A 31-byte program appended 257 running balances. Changing one byte preserved the final sum while changing the caller’s list. A reusable traversal needs to express what gets appended and when a write becomes visible. Running that image on a longer array tests execution. Encoding a different program with the same vocabulary tests reuse. [History evidence](experiments/0012-BalanceHistory/README.md#v1-results)

Recovered space can also buy **more meaning at the same size**. Weightless already encodes checked Add with an enforced nonnegative-result requirement in the same 19 bytes as the plain baseline. Future experiments should measure both how much smaller an equivalent program becomes and what additional guarantee fits in the original budget. [Contract and distinguishing inputs](docs/SETTLEMENT-2026-11-23.md)

## How we will recognize tenfold compaction

1. **Freeze before seeing the evaluation programs.** Develop the vocabulary on known programs, then publish a version of its entries, encoder, decoder, and baseline selection rule. Use independently selected, held-out programs spanning several behaviors and compositions. Changing a keyword after seeing a case makes that case development evidence. Evaluate the revised vocabulary on a fresh holdout.
2. **Compare complete representations of the same work.** Use the strongest applicable existing encoding under the same contract. For the known 4,095-Add control, the current program image to beat is 21 bytes. Declare the host both sides assume. Count the bytes where they are stored, including framing, padding, operands, and bindings. Charge an embedded schema to every image that carries it. Charge a shared dictionary or decoder extension its full size once per collection. Show the first program’s cost, the cost of adding another, and the aggregate. An operation the new vocabulary cannot express needs a counted fallback or an explicit coverage failure.
3. **Replay what the caller can observe.** Open the saved programs in a fresh process and compare them with independent references. Each contract specifies the relevant return value, fault details, object identity, ordered writes, and state visible after failure. Keep a changed program or input that distinguishes a plausible wrong implementation. A counterexample refutes that equivalence. Passing the corpus supports the tested cases. A proof carries the assumptions of its model. [Product replay and controls](docs/PRODUCT-SETTLEMENT-2026-11-24.md)
4. **Publish the denominator.** The milestone requires `total baseline bytes / total candidate bytes >= 10` for the full held-out collection, with every program represented and every required observation matching. Publish the actual images, shared costs, per-program and per-family sizes, and a replay command. Readers should be able to see whether a single repeated pattern accounts for most of the gain. Execution time and memory are separate measurements.

Independent labs can explore different keywords, contracts, and implementations from the same version. A smaller image, a stronger guarantee at equal size, and a counterexample that rules out an apparent freedom each tell us something different about the hypercube.
